# overview.md
## 1 文档概述
本文档针对Kubernetes‑v1.32集群日志平台，对比 **Loki、ClickHouse、ELK(Elasticsearch)** 三套主流日志存储方案，从架构原理、资源开销、检索能力、适用场景、运维成本、生产短板多维度完成选型对比，用于企业日志架构落地决策。

整体采集层统一采用 Fluent‑Bit 作为节点侧采集Agent；三种方案主要差异集中在缓冲、存储、查询链路。

## 2 三套方案整体数据流
### 2.1 Loki 方案（轻量容器日志首选）
`Fluent‑Bit → Loki → Grafana`
- 可选增加 Kafka 作为高并发集群消息缓冲
- 标签索引，日志正文压缩存储，不对全文构建倒排索引

### 2.2 ELK‑Elasticsearch 方案（全文检索）
`Fluent‑Bit → Kafka → Elasticsearch → Grafana/Kibana`
- 全字段倒排索引，支持模糊检索、分词搜索、短语匹配

### 2.3 ClickHouse 方案（日志统计、审计、大盘）
`Fluent‑Bit → Kafka → ClickHouse → Grafana`
- 列式存储、MergeTree分区引擎，面向海量日志聚合、分组统计、审计报表

## 3 多维度详细对比表
|对比维度|Loki|Elasticsearch(ELK)|ClickHouse|
|---|---|---|---|
|核心索引机制|标签Label索引，正文无索引|全字段倒排分词索引|MergeTree稀疏主键索引 + 时间分区|
|磁盘占用|极低，高压缩比(8‑15倍)|很高，索引体积大于原始日志|中等，列式存储压缩优秀|
|CPU/内存开销|低，适合中小型集群|极高，段合并、索引占用大量资源|中等，聚合计算消耗内存|
|日志检索方式|标签筛选 + 正文正则匹配|分词、模糊、全文检索、短语查询|SQL条件过滤、分区裁剪、聚合统计|
|查询语法|LogQL|DSL查询语句|标准SQL|
|写入性能|优秀|普通，分片合并存在IO压力|优秀，适合大批量日志写入|
|典型短板|不适合复杂全文检索；标签基数爆炸风险|资源消耗高、分片管理复杂、运维沉重|不适合模糊关键字检索，上手门槛偏高|
|日志留存策略|Compactor组件TTL清理|ILM索引生命周期冷热分层|数据表分区TTL自动过期|
|最佳适用场景|容器标准输出、Pod故障排查、日常运维日志|业务日志关键字检索、异常堆栈搜索|集群审计日志、访问日志、PV‑UV报表、数据分析|
|K8s适配友好度|极高，专为云原生日志设计|一般，需要复杂分片规划|良好，适合大数据量统计场景|

## 4 架构分层选型建议
### 4.1 标准生产基线架构（推荐）
1. **容器普通业务日志 → Loki**
日常Pod控制台输出、微服务运行日志、故障排查日志，优先选用Loki，节约服务器资源。
2. **需要全文检索的业务日志 → Elasticsearch**
例如订单、支付、业务异常堆栈，需要频繁进行关键字模糊检索。
3. **K8s审计日志、节点访问日志、监控大盘日志 → ClickHouse**
依靠SQL做各类统计：错误日志排行、各个Namespace日志量、接口访问频次。
4. 大规模集群统一前置 Kafka 消息队列，实现流量削峰、上下游解耦、多存储分发。

## 5 集群规模选型标准
1. 节点数 ≤30，中小型集群：**全套Loki**，架构简单、运维成本最低
2. 节点数 30‑100：Fluent‑Bit + Kafka，业务日志Loki，检索类日志分流ES
3. 节点数＞100大型集群：三架构共存，日志按照业务类型物理分流

## 6 通用生产约束
1. 采集层统一使用Fluent‑Bit，节点侧完成日志过滤、字段精简、敏感数据脱敏，减轻存储层压力
2. Loki严格管控标签白名单，禁止traceId、requestId、随机ID作为标签，规避标签基数爆炸
3. Elasticsearch禁止单分片超过50GB，依靠ILM做索引生命周期管理
4. ClickHouse必须以时间作为分区键，所有查询携带时间条件触发分区裁剪
5. 审计日志独立流水线、独立Topic、独立数据表，不和普通业务日志共用存储资源
