# component‑selection.md
## 1 选型前置约束
基于当前集群环境基线：K8s‑v1.32、containerd容器运行时、NFS‑SC持久化存储、GitOps配置管理、离线MinIO存放helm安装包；  
组件选型严格围绕**资源开销、可维护性、稳定性、生态适配、离线部署、日志丢失风险、运维成本**七个维度对比评估。  
整体选型结论：采集器优先 Fluent‑Bit；主存储选用 Loki；全文检索场景备选 Elasticsearch；海量日志分析场景选用 ClickHouse；可视化组件 Grafana。

## 2 日志采集Agent横向对比
|组件|资源占用|管道能力|本地缓冲|K8s原生适配|优缺点|生产选型结论|
|---|---|---|---|---|---|---|
|Fluent‑Bit|极低|插件生态齐全，支持日志解析、过滤、修改字段；复杂预处理能力一般|支持内存缓冲，可配置磁盘缓冲|成熟稳定，Kubernetes环境行业标配|占用资源小、部署轻量化、文档丰富、社区案例多；高级流水线处理功能弱于Vector|**首选采集组件**|
|Vector|低|Rust高性能，丰富插件，支持动态配置重载|磁盘缓冲区、内存缓冲|完善，原生支持K8s标签注入|性能强悍、配置热加载；集群落地案例少于Fluent‑Bit|备选，高吞吐日志场景使用|
|Fluentd|很高|Ruby插件，自定义处理灵活|缓冲机制完善|适配良好|功能强大，但是内存开销大、容易出现内存溢出|不推荐生产节点侧部署|

### Fluent‑Bit 选定理由
1. C语言开发，资源消耗极低，大批量节点部署不会带来过高节点负载
2. 云原生行业主流标准采集组件，K8s、containerd生态适配完善，大量生产落地经验
3. 内置tail文件监听、容器日志解析、kubernetes元数据过滤器，一键注入namespace、pod、workload标签
4. 支持内存缓冲与磁盘持久化缓冲，网络抖动、后端存储故障时落地缓存，降低日志丢失概率
5. 配置文件简洁，支持热重载；自带监控指标，可以对接Prometheus观测日志读取量、丢弃量、发送延迟
6. 单二进制程序，依赖极少，离线环境打包部署简单

## 3 日志存储引擎横向完整对比（Loki / Elasticsearch / ClickHouse）
|存储组件|底层架构|索引机制|资源开销|查询能力|存储成本|典型适用场景|
|---|---|---|---|---|---|---|
|Loki|分块压缩存储，标签索引|仅对标签建立索引，日志正文无索引|低|标签筛选、正则匹配检索|很低|容器标准输出日志、集群轻量化日志平台、故障排查|
|Elasticsearch|倒排索引、分片架构|全字段倒排索引，支持分词|很高|全文分词检索、模糊搜索、日志聚合分析|高|业务日志关键字深度检索、日志分词、ELK传统架构|
|ClickHouse|列式存储、分区表、主键索引|列式主键索引、二级稀疏索引、分区索引|中等|高性能聚合统计、海量日志报表、多维度数据分析|中等|超大吞吐量日志、日志指标统计、大屏分析、审计日志|

### 各存储详细选型解析
#### 3.1 Loki（集群默认主存储）
1. 只对 namespace、pod、deployment、node 这类标签建立索引，日志正文不构建索引，磁盘占用远低于ES
2. 原生适配Grafana，日志‑监控指标一套可视化平台
3. 组件拆分清晰：Distributor、Ingester、Query、Ruler，便于独立扩缩容
4. 支持基于时间的日志生命周期、过期自动清理
5. 适配集群NFS存储类完成持久化Chunk存储

#### 3.2 Elasticsearch 适用场景
1. 需要日志正文分词检索、模糊匹配、短语搜索
2. 业务日志结构复杂，需要针对多个业务字段筛选
3. 存量ELK架构、团队具备成熟ES运维经验
> 缺点：内存开销巨大，JVM堆内存难调优；分片运维复杂；磁盘占用高，不适合超大规模集群基础容器日志。

#### 3.3 ClickHouse 适用场景
1. 列式存储天然适合海量日志聚合、PV统计、错误数、耗时分组统计
2. 日志量超大，每日TB级日志吞吐量，需要高性能SQL分析
3. 集群审计日志、安全日志、业务访问日志做大盘报表
4. 可接收Fluent‑Bit推送，依靠SQL语句灵活做多维度筛选

**ClickHouse对比ES核心差异**
1. ES擅长全文检索；ClickHouse擅长聚合、分组、统计、报表
2. ES为行式倒排索引；ClickHouse列式存储，大批量统计IO开销更低
3. ClickHouse资源开销低于Elasticsearch，无沉重JVM依赖
4. ES适合人工排查日志；ClickHouse适合程序自动统计日志指标

## 4 可视化组件选型
1. **Grafana（选定）**
- 原生深度兼容Loki数据源；同时支持ClickHouse、Elasticsearch数据源
- 可实现监控指标、链路追踪、日志三者面板统一
- 支持日志告警、日志关键词阈值告警
- 权限体系对接K8s‑RBAC，区分开发人员日志查看权限
2. Kibana：仅搭配Elasticsearch使用，平台技术栈需要维护两套可视化组件，架构较重，不作为首选

## 5 辅助周边组件选型
1. 告警组件：Alertmanager，复用现有Prometheus告警栈，无需新增独立告警系统
2. 配置管理：Argo‑CD GitOps，Fluent‑Bit全部yaml、pipeline配置存入Git仓库
3. 离线部署：helm chart存放至内网MinIO对象仓库
4. 缓冲方案：Agent开启磁盘缓冲，应对后端存储短时不可用

## 6 三套完整技术方案
### 方案A（标准生产方案，正式采用）
> Fluent‑Bit + Loki + Grafana
适合大规模容器集群、海量stdout日志、追求低资源开销、轻量化可观测体系。

### 方案B（全文检索增强方案）
> Fluent‑Bit + Elasticsearch + Kibana/Grafana
适合业务日志需要分词检索、日志内容深度解析、日志大数据检索场景。

### 方案C（海量日志分析方案）
> Fluent‑Bit + ClickHouse + Grafana
适用于日吞吐量庞大、需要多维度聚合统计、安全审计日志分析场景。

## 7 组件避坑约束
1. 禁止节点同时部署多款采集Agent，避免文件监听冲突、重复采集日志
2. Loki不要过度添加标签，标签基数过大会造成索引膨胀、查询性能下降
3. Agent必须配置资源Limit，防止日志洪峰抢占节点CPU内存资源
4. 采集、存储、可视化组件分开独立命名空间部署，环境资源隔离
5. Fluent‑Bit磁盘缓冲目录务必挂载宿主机本地磁盘，缓冲数据跟随节点本地存储
6. ClickHouse需要做好时间分区策略，依靠分区裁剪加速日志查询；ES严控分片数量与堆内存上限
