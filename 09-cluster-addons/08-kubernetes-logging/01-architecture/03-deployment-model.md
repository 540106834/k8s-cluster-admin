# deployment‑model.md
## 1 前置环境基线
- Kubernetes v1.32，容器运行时 containerd
- 日志采集组件：Fluent‑Bit（DaemonSet 节点代理）
- 存储引擎支持 Loki / Elasticsearch / ClickHouse 三类后端
- 持久化存储：nfs‑sc StorageClass
- 配置管理：GitOps + ArgoCD，离线 Helm‑Chart 托管于 MinIO
- 整体架构：**节点侧采集Agent + 后端独立存储服务**

## 2 三类主流日志部署模型对比
### 2.1 模型一：DaemonSet 分布式节点Agent（生产主推方案）
#### 拓扑结构
1. Fluent‑Bit 以 DaemonSet 部署在全部 Worker 工作节点，每节点单个采集Pod
2. Pod 挂载宿主机日志目录：`/var/log`、containerd容器日志目录、kubelet日志路径
3. 控制节点通过节点亲和性禁止调度日志采集Pod
4. Fluent‑Bit 读取本机日志，完成解析、标签注入、过滤、脱敏
5. 根据业务场景推送至对应的存储后端：Loki / ES / ClickHouse
6. 存储组件独立部署专属命名空间，使用 StatefulSet 绑定 NFS 持久化存储

#### 优势
1. 本地读取日志文件，不存在跨节点文件IO开销
2. 故障域隔离，单个Agent异常仅影响当前节点日志采集
3. 支持宿主机磁盘缓冲，后端存储宕机、网络抖动时缓存日志，降低丢失风险
4. 集群新增节点会自动拉起采集Pod，跟随集群节点弹性扩容
5. 采集流量内网转发，不需要侵入业务容器，无需 Sidecar

#### 短板
1. 节点规模庞大时，Fluent‑Bit实例数量较多，需要统一管控配置
2. 必须配置 CPU、内存 Limit，防止日志突发流量抢占节点业务资源

#### 适用场景
全量容器标准输出日志、大规模生产集群、日志丢失风险零容忍，为本环境默认架构。

---

### 2.2 模型二：集中式采集架构
#### 拓扑结构
1. 集群内部部署固定数量的采集服务，不采用节点DaemonSet
2. 业务容器通过 Sidecar、syslog、socket 将日志转发给集中采集服务
3. 由集中采集组件统一处理日志之后写入存储后端

#### 优势
- Agent实例数量少，配置维护简单

#### 短板
1. 采集服务容易成为全集群日志流量瓶颈
2. 需要改造业务容器，侵入业务Pod生命周期
3. 节点网络故障时无法本地缓存，日志丢失概率很高
4. 日志多一层网络转发，传输延迟更高

#### 适用场景
仅小规模测试集群，正式生产环境禁止选用

---

### 2.3 模型三：混合部署模式
#### 拓扑结构
1. 普通工作节点：DaemonSet‑Fluent‑Bit 采集容器 stdout/stderr
2. 管控节点、审计节点单独定制采集流水线，采集 apiserver 审计日志
3. 部分业务容器开启 Sidecar，采集容器内部落地的业务文件日志
4. 所有日志统一汇总至后端存储

#### 优势
采集方式灵活，可以针对不同日志源定制采集策略

#### 短板
架构复杂、两套采集链路容易出现重复采集；配置维护、故障排查成本高

#### 适用场景
仅特殊业务日志场景做局部适配，不作为整体方案

## 3 三类存储后端对应的部署细节
### 3.1 Loki（默认轻量化日志存储）
1. Distributor：多副本 Deployment，接收 Fluent‑Bit 上报流量、负载均衡
2. Ingester：StatefulSet，绑定 nfs‑sc 持久化日志Chunk
3. Query、Ruler 独立部署，负责日志检索、日志告警规则评估

### 3.2 Elasticsearch（全文检索场景）
1. ES 集群采用 StatefulSet 多节点部署，master、data、ingest节点角色拆分
2. 分片与副本提前规划，持久化存储对接NFS‑SC
3. Fluent‑Bit 通过 http 输出插件直接投递数据

### 3.3 ClickHouse（海量日志聚合分析）
1. 采用 StatefulSet 部署，开启按时间自动分区表
2. 依靠NFS存储磁盘表文件
3. Fluent‑Bit 输出插件推送至 ClickHouse HTTP 接口

## 4 生产环境硬性部署规范
1. Fluent‑Bit 使用节点亲和性，禁止调度至控制平面节点
2. 采集组件、存储组件、Grafana 分别放置独立命名空间，资源隔离
3. Fluent‑Bit 开启磁盘缓冲目录，挂载宿主机本地磁盘
4. Agent 设置 Requests/Limits，约束CPU和内存，避免日志洪峰抢占业务资源
5. Agent 与存储后端之间开启 TLS 传输加密
6. 所有解析规则、过滤规则、脱敏配置交由Git仓库管理，ArgoCD自动同步重载
7. 存储组件调度至资源充足的专属节点，使用节点标签隔离资源

## 5 三种部署模式综合对比表
|部署模式|故障隔离|日志丢失风险|传输延迟|运维复杂度|生产选用|
|---|---|---|---|---|---|
|DaemonSet节点分布式|优秀|低，本地磁盘缓冲|最低|中等|✅ 默认方案|
|集中式采集|很差|高|偏高|简单|❌ 不推荐|
|混合部署模式|一般|中等|中等|很高|❌ 特殊场景局部使用|
